# make-knowledge-cards

把一篇文章变成 **5~8 张知识卡片** 的 Agent Skill（遵循 [Agent Skills](https://github.com/openai/skills) 规范）。

每张卡片只讲一个知识点，包含四要素：**标题 · 核心知识 · 简明解释 · 例子或自测问题（二选一）**。

## 解决什么问题

读完一篇干货文章，想复习时往往只剩"好像看过"的印象：普通摘要面面俱到却记不住，自己手工整理卡片又费时费力、标准不一。

本 Skill 把这一步标准化——从文章原文中提取**真正重要的知识**，自动生成结构统一、可直接用于复习的知识卡片集，同时保证：

- **一卡一点**：每张卡片只讲一个知识点，不混装
- **只取不造**：全部内容可溯源到原文，禁止编造原文没有的信息
- **自动去重**：重复表述、同一知识点的不同粒度复述自动合并
- **不凑数量**：原文信息不足 5 个知识点时按实际数量出卡并说明，宁缺毋滥

## 主要功能

- **输入**：直接粘贴的文章文本，或本地 `.md` / `.txt` 文件
- **输出**：一份 Markdown 知识卡片集，开头一行注明来源与张数
  - 常规输出 5~8 张，按"由基础到进阶"排序，形成学习路径
  - 知识点超过 8 个 → 保留最重要的 8 个，并用一行注明略去的次要内容
  - 知识点不足 5 个 → 按实际数量输出，并用一行说明原文信息不足
- **卡片格式**：`例子` 与 `自测` 二选一——原文有具体案例就给例子，没有则给自测问题（附原文可查的答案）
- **语言跟随原文**：原文是中文就输出中文卡片，除非你另行指定
- **张数可调**：明确要求其他张数时按你的要求执行，其余质量规则不变
- **暂不支持**：网页抓取、PDF 解析、Anki 导出、图形界面（会明确说明并给出替代建议，如改为粘贴文本）

## 安装方法

本 Skill 是纯指令型（无脚本、无第三方依赖），安装即"复制目录"：

1. 获取本项目（下载或克隆到本地）
2. 把 `skills/make-knowledge-cards/` 整个目录复制到你的 Agent 技能目录：

   | Agent | 技能目录 |
   |---|---|
   | Codex（OpenAI skills） | 项目下 `skills/` |
   | Claude Code | 项目下 `.claude/skills/` 或全局 `~/.claude/skills/` |
   | OpenClaw | `~/.openclaw/skills/` |

3. （可选）用官方脚本校验结构：

   ```bash
   python3 quick_validate.py skills/make-knowledge-cards
   # Skill is valid!
   ```

## 使用方法

把文章给 Agent，用自然语言触发即可，例如：

- 「把这篇文章做成知识卡片」+ 粘贴文章
- 「用 make-knowledge-cards 处理 ./notes/rag.md」
- 「把这段文字整理成 6 张复习卡片」（显式指定张数）
- 「处理完把卡片存到 ./cards/rag.md」（要求保存文件时按指定路径输出）

## 输入输出示例

**输入**（`git_tutorial.txt` 节选）：

```text
Git 分支协作实用指南

黄金法则：永远不要 rebase 已经推送到公共分支的提交。rebase 会改写提交的
历史，如果别人已经基于你的旧提交开始工作，改写历史会让大家的仓库状态混乱……
一旦推送出去，就用 merge 来同步。
```

**输出**（节选，完整输出含全部卡片与来源行）：

```markdown
# 知识卡片：Git 分支协作实用指南（7 张）

## Card 1 · merge 与 rebase 的区别

- **核心知识：** merge 保留完整分支历史并生成合并提交，rebase 把提交搬到目标
  分支最新提交之后使历史成为直线。
- **简明解释：** merge 把两条分支的历史完整接起来，并生成一个合并提交；rebase
  把你的提交搬到目标分支最新提交之后。两者没有绝对优劣，按场景选择。
- **自测：** merge 和 rebase 产生的历史形态有什么不同？（答案：merge 保留完整
  历史并生成合并提交；rebase 使历史保持一条直线。）

## Card 2 · 黄金法则：不 rebase 公共提交

- **核心知识：** 永远不要 rebase 已经推送到公共分支的提交。
- **简明解释：** rebase 会改写提交历史。如果他人已基于你的旧提交工作，改写
  历史会让大家的仓库状态混乱，合并时产生大量冲突。一旦推送出去，就用 merge
  同步。
- **例子：** 提交已经推送到公共分支后，改用 merge 来同步，而不是 rebase。
```

**信息不足时的输出**（短文只提炼出 2 个知识点，不凑数）：

```markdown
# 知识卡片：读《深度工作》有感（2 张）
……
> 注：这篇短文提供的独立知识点不足 5 个（其余内容为个人感想，不含可迁移
> 知识），按实际提取结果输出 2 张卡片，未凑数。
```

**知识点超过 8 个时的输出**（保留最重要 8 张 + 略去说明）：

```markdown
> 注：原文还包含各偏差的对抗方法、商业应用案例，以及通用减偏方法，属次要
> 内容，本卡片集未收录。
```
